Memory Architecture and Inference Optimization for Agentic SOC Systems

Memory Architecture Design for Agentic SOC Systems

Agentic Security Operations Center (SOC) systems employ multiple specialized AI agents to automate tasks like alert triage, threat intelligence analysis, vulnerability management, and incident response. Unlike simple stateless models, these agentic AI systems leverage memory to retain context and learn from past interactions, improving their decision-making and adaptability. Each agent role has distinct data inputs and contextual needs, requiring a tailored memory architecture:

Alert Triage Agents: Focus on ingesting real-time security alerts (e.g. SIEM events) and determining their priority. They need short-term memory of the current alert’s details and recent related events to avoid treating each alert in isolation. They also benefit from episodic memory of historical alert patterns (e.g. seeing if a similar alert occurred before) and semantic knowledge of known false positives or typical attack signatures. Procedural knowledge (e.g. playbook steps for triage) may be applied to consistently decide when to escalate an alert.

Threat Intelligence Agents: Continuously gather and enrich indicators of compromise (IOCs) from threat feeds. They rely heavily on semantic memory – a long-term knowledge base of threat actor profiles, IOC reputations, and tactics/techniques (often structured via standards like STIX). They use episodic memory to recall past threat campaigns or related incidents and short-term memory for the current feed items being analyzed. Procedural memory helps in applying analytical tradecraft (for example, pivoting from one IOC to related indicators automatically).

Vulnerability Management Agents: Handle data on asset configurations, software versions, and discovered vulnerabilities. They leverage semantic memory for known vulnerability information (e.g. CVE details, CVSS scores) and episodic memory to track each asset’s vulnerability history (when a vulnerability was detected or patched). Short-term memory is used for the current scan or assessment context, and procedural routines guide steps like notifying asset owners or recommending patches.

Incident Response Agents: Coordinate complex, multi-step investigations and containment actions during security incidents. They maintain an episodic memory of the incident timeline – recording key events and actions taken as the “episode” unfolds. They draw on semantic memory of attack techniques (e.g. MITRE ATT&CK tactics, malware knowledge) to interpret evidence in context. A rich procedural memory is critical: these agents follow and adapt playbooks (learned or hard-coded sequences of actions) for containment, eradication, and recovery. Short-term working memory ties it all together, keeping the current investigation context (latest alerts, findings, and decisions) readily available in each reasoning step.


Differences in Security Data Taxonomies: Each agent deals with different data schemas and taxonomies, which poses a challenge for unified memory. Alerts are often categorized by event type or MITRE ATT&CK technique, threat intelligence uses its own schemas for actors, campaigns and IOCs, vulnerability data revolves around CVE identifiers and asset inventories, and incident reports have custom fields and narratives. These divergent taxonomies make it difficult for agents to share context directly – an alert’s source IP might need to be correlated with threat intel feeds or vulnerability databases, but the data formats differ. In practice, integrating these sources requires significant normalization and mapping. Modern SOC platforms recognize this data integration challenge: agents must correlate information across network logs, EDR telemetry, vuln management platforms, and threat intel feeds, which is essential for accurate threat assessment but represents a significant technical challenge in production. Initiatives like the Open Cybersecurity Schema Framework (OCSF) aim to define a common, extensible data model to streamline such integration. Even with standard schemas, maintaining context consistency across agents is non-trivial – for example, an “asset ID” in the vuln database must link to the same system referenced by an IP in an alert. Without careful data engineering, an agentic SOC can devolve into siloed “islands of automation” rather than a cohesive intelligence system.

Memory Types and Implementation Strategies: Researchers categorize an agent’s memory analogously to human memory. A robust agent architecture layers multiple memory types to cover immediate context, specific past events, general knowledge, and skills:

Short-Term Memory (STM): A limited working memory of recent inputs and observations, crucial for maintaining context within a single session or task. In implementation, STM is often provided by the context window of the language model or a rolling buffer of the latest dialogue or data. For example, a chatbot-based SOC assistant might include the last N user queries and agent answers in the prompt so it “remembers” what’s going on. This memory is transient – it resets between sessions – and is typically realized by keeping a sliding context of the most recent log lines, alerts, or messages. While STM enables continuity (e.g. linking a follow-up question to the previous answer), it alone is insufficient for long-term learning or personalization.

Episodic Memory: The storage of specific past experiences or events that the agent can later recall. In a SOC context, episodic memory might be a case history database or incident log that the agent can query: e.g. “Have we seen a login from this IP before?” or “What actions were effective last time we saw malware X on this server?”. Agents implement episodic memory by logging key events, actions, and outcomes in a structured format (such as case records or time-stamped logs). This allows case-based reasoning – the agent can draw parallels to past incidents when confronted with a new one. Effective episodic memory requires indexing and retrieval: the agent must find the right past incident or alert sequence relevant to the current situation (often via search or similarity matching).

Semantic Memory: Long-term factual knowledge that the agent has learned or been provided. This includes generalized information like security policies, threat intelligence databases, network diagrams, known vulnerabilities, and so on. Semantic memory is typically implemented with knowledge bases or vector databases that the agent can query using embeddings. For instance, an agent can use retrieval-augmented generation (RAG) to fetch relevant facts from an internal wiki or threat intel corpus and incorporate them into its reasoning. Unlike episodic memory’s specific events, semantic memory covers broader domain understanding – e.g. knowing that “Mimikatz is a credential-dumping tool” or “CVE-2023-1234 is a critical remote code execution vulnerability in Apache HTTP Server”. Storing this as structured data or vectors allows the agent to ground its output in authoritative information (reducing hallucinations and ensuring up-to-date knowledge).

Procedural Memory: Encodes skills and action sequences – the “know-how” that allows the agent to perform tasks automatically based on learned experience. For AI agents, this might take the form of fine-tuned policies or scripts for multi-step tasks. For example, a procedural memory could be a learned policy (via reinforcement learning or expert demonstrations) for how to respond to a phishing email: steps to isolate the affected account, search for similar emails, notify users, etc. In implementation, procedural memory can be hard-coded playbooks in an orchestration engine or policies embedded in the model via fine-tuning. Over time, an agent can refine its procedural memory by learning which actions lead to successful outcomes (similar to how humans gradually perform tasks more intuitively through repetition). This type of memory makes the agent’s behavior more efficient and consistent – the agent doesn’t have to reason from scratch for every recurring task, it can “remember” how to do it. For instance, a vulnerability management agent might have a stored procedure for “if a critical vuln is found on a public-facing server, then schedule patch within 24 hours and update the risk dashboard.”


Critically, these memory types work in unison. An agentic SOC architecture should allow agents to use all layers: short-term context for the immediate situation, episodic memory to recall similar cases, semantic lookups for factual enrichment, and procedural knowledge to execute best-practice responses. The CoALA cognitive architecture paper from Princeton underscores that this blend of memory forms the backbone of truly context-aware, goal-driven agents. In practice, implementing this means combining data stores and techniques: e.g. a vector database for semantic knowledge, time-indexed event journals for episodic memory, and incorporating organizational Standard Operating Procedures (SOPs) into the agent’s training or prompt (procedural memory). As one example, an AI SOC analyst investigating an incident might retrieve previous incident reports and relevant threat intel (episodic + semantic memory) and then follow an automated remediation playbook (procedural memory) – all while conversing with a human analyst with awareness of the last question asked 5 seconds ago (short-term memory).

Challenges in Combining Memories: Designing memory architecture is not just about creating these stores, but making them work together seamlessly. One challenge is retrieval efficiency – storing too much data can slow down lookups or overwhelm the context window. Agents must be smart about what to recall (e.g. using relevancy filters or summarizing long histories). Another challenge is avoiding contradictory or outdated memories. For instance, an agent’s semantic memory might contain a deprecated policy, while its procedural memory has a new workflow – careful governance is needed to update or invalidate old knowledge. Ensuring consistency between agents is also key; if the threat intel agent learns a new fact (semantic memory), the alert triage agent should ideally benefit from it too. This may require a shared memory layer or inter-agent communication protocols. In advanced implementations, agents share reasoning traces and outcomes with each other – e.g. a triage agent might tag an alert with an incident ID so that the incident response agent’s episodic memory can link the ongoing incident with that initial alert. Memory thus becomes a distributed system problem within an agent ensemble. The Trellix production SOC case study highlights that integrating diverse data sources and maintaining consistent data quality across platforms was one of the most difficult aspects of their LLM-powered SOC deployment. Robust memory architecture, combined with data integration standards, is the linchpin that allows multiple agents to form a coherent “collective intelligence” rather than disjointed bots.

Mini-SGLang: Inference Optimization for SOC Agents

To serve these memory-augmented SOC agents efficiently, we need an inference engine that can handle large language model workloads with high throughput and low latency. Mini-SGLang is a lightweight, high-performance LLM inference framework designed for this purpose. It retains many advanced optimizations from its parent project SGLang, but in a compact, 5K-line codebase intended for easy understanding and rapid prototyping. Mini-SGLang is capable of serving large models (e.g. Llama-2 or Qwen families) with state-of-the-art performance, making it well-suited as the backbone for SOC agents that rely on fast LLM responses. Key inference optimizations provided by Mini-SGLang include:

Speculative Decoding: This technique accelerates text generation by allowing a smaller “draft” model to propose multiple tokens in advance, which the large model then verifies, rather than having the large model generate every token sequentially. In Mini-SGLang (and SGLang), speculative decoding follows approaches like EAGLE decoding to dramatically improve throughput. For example, using a speculative decoding strategy (EAGLE-2 or EAGLE-3), an 8B LLaMA model’s generation throughput can increase from ~158 tokens/s to 373 tokens/s on a single GPU. The draft model’s guesses that the main model accepts allow skipping a lot of redundant computation. In an SOC context, speculative decoding is especially useful when an agent needs to produce longer outputs (e.g. an incident summary or detailed threat report) – it helps generate those reports faster by utilizing parallelism between models. The trade-off is managing accuracy (there is a chance the large model rejects the draft tokens and falls back to step-by-step generation), but with careful tuning this approach yields significant speed-ups with minimal quality loss. SGLang’s implementation is considered one of the fastest open-source versions of this technique. By using speculative decoding, agents can maintain interactivity even when using very large models, as the latency per token is reduced.

Streaming Output: Mini-SGLang supports token streaming, meaning partial results are sent back as soon as they are generated, rather than waiting for the full completion. This is crucial for interactive AI agents and real-time SOC workflows. Streaming improves perceived latency – an analyst can start seeing the beginning of an answer or incident report while the model is still generating the rest. SGLang’s architecture was built around making inference “responsive and fluid,” enabling live token streaming without adding overhead. In practice, streaming output is implemented via an asynchronous server that flushes tokens over the API (or WebSocket) as they arrive. For example, if an incident response agent is explaining steps it’s taking, the SOC interface can show each step as it’s formulated. This also allows for possible mid-flight corrections or early terminations if needed. Compared to non-streaming (where one must wait perhaps 30 seconds for a full report), streaming can significantly enhance the usability of AI agents in a SOC, especially under time-sensitive conditions. Mini-SGLang integrates streaming smoothly with its scheduling so that token-by-token output doesn’t stall new requests – it continuously balances work on ongoing streams vs new queries.

Overlap Scheduling: A major performance innovation in SGLang/Mini-SGLang is overlap scheduling, which hides CPU overhead by overlapping it with GPU computation. In a naive serving pipeline, after the GPU finishes generating some tokens, there is often CPU work to do: preparing the next batch of requests, running tokenization or post-processing, etc. If done serially, the GPU might sit idle waiting for the CPU, under-utilizing expensive hardware. Mini-SGLang avoids this by decoupling and parallelizing those tasks – while the GPU is busy computing the current batch’s outputs, the CPU asynchronously prepares the next batch of inputs in parallel. By the time the GPU is free, the next batch is ready to go, resulting in almost 100% GPU utilization. This is illustrated in performance profiles: with overlap scheduling, GPU idle time is eliminated, whereas without it, one observes gaps where the GPU waited for the CPU. For SOC agents, which may need to handle dozens of concurrent requests (e.g. analyzing multiple alerts at once or handling a flurry of user queries), overlap scheduling ensures maximum throughput. The CPU can be tokenizing incoming alert data, batching new queries, or doing JSON formatting of outputs at the same time the GPU is generating text. Mini-SGLang’s design includes a zero-overhead CPU scheduler to achieve this tight coupling, effectively making the inference process pipeline parallel. This leads to more predictable latency and better scalability, since adding more CPU cores can keep feeding the GPUs efficiently.

Radix Cache (Prefix KV Cache Reuse): Mini-SGLang implements an advanced KV caching strategy known as Radix Attention to maximize reuse of previous computation across requests. During Transformer-based text generation, the model produces Key/Value (KV) tensors for each token in the context – essentially a cache of attention states. If multiple requests share the same prefix (e.g. many alerts start with the same company header, or multiple queries use the same system prompt describing the SOC policies), SGLang’s Radix Cache will store that prefix’s KV once and reuse it for all requests. This avoids recomputing the heavy self-attention for the shared prefix tokens. The approach is akin to the prefix caching in vLLM, which significantly cuts down latency by skipping redundant work. For example, if an alert triage agent asks the model to analyze an alert and then asks a follow-up question with the same alert description included, the second request can hit the KV cache and skip computing the first N tokens again, dropping time-to-first-token from seconds to sub-second. More broadly, in multi-user or multi-agent scenarios common in SOCs, many requests will have overlapping context (common instructions, repeated incident details), so a high cache hit rate dramatically improves efficiency. Industry experts even note that KV-cache hit rate is the single most important metric for production AI inference, as cached tokens can be processed an order of magnitude cheaper and faster than cache misses. Mini-SGLang’s Radix cache uses a tree (radix trie) structure to organize prefix tokens so that any shared prefix yields a cache hit. This is especially beneficial for workloads like chat interactions (which naturally have a growing prefix of conversation history) and batched alert processing (where many alerts might share common fields or formatting). In essence, Radix caching gives the model a form of short-term memory of recent prompts at the system level – once it has seen a prompt fragment, it can recall the “computation” for it instantly later.

Distributed and Parallel Scheduling: Traditional transformer inference typically processes one request at a time per GPU (or a static batch) and relies on the user to scale this across machines. By contrast, Mini-SGLang is built for distributed, multi-model serving. It supports tensor parallelism to split a large model across multiple GPUs for faster inference, as well as multi-GPU data parallelism for serving many requests in parallel. In production on an NVIDIA H100 cluster, Mini-SGLang can use 4 or 8 GPUs in tandem to host a single large model (e.g. a 70B-parameter model) or to host multiple model shards. More importantly, the scheduler is cache-aware and cluster-aware: in a multi-node deployment, it aims to route requests such that those with shared prefixes go to the same GPU (or node) to maximize cache hits. This addresses a key scaling challenge – naive load balancers might scatter related requests and nullify the prefix caching benefits, leading to redundant computation on each node. SGLang’s approach (also seen in IBM’s LLM-D project) is to give the scheduler visibility into the KV cache state of each node so it can smartly place new requests where the needed prefix already resides. The result can be order-of-magnitude performance gains in distributed settings: one case showed 57× faster response and double throughput by avoiding cache misses across replicas. In summary, Mini-SGLang’s distributed scheduling ensures that as SOC agents scale out to multiple servers or cloud instances, they still benefit from local cache reuse and balanced loads. Additionally, the framework supports continuous batching, dynamically grouping incoming requests by model and context similarity to optimize GPU utilization. This means whether a single analyst question or 100 alert analyses arrive concurrently, the engine can batch them efficiently without high latency. In contrast, traditional pipelines often have fixed batch sizes or struggle with varying sequence lengths, leading to stalls when short and long requests mix. Mini-SGLang’s batch scheduler and support for prefill-decode disaggregation (executing the input encoding and output decoding phases separately, possibly on different hardware) further improve utilization in complex workflows.


Comparison to Traditional Transformers Pipelines: Mini-SGLang’s feature set can be understood by comparing it to a baseline “naïve” transformer serving pipeline (e.g. using the basic HuggingFace generate() in a loop). In a traditional setup, each inference request is processed independently, end-to-end on a single device, with no knowledge of other requests. There is no sharing of computation between requests – even if two inputs differ only in one token, the model will recompute the entire sequence for both. This yields suboptimal performance for the SOC use case in several ways:

Higher Latency per Request: Without speculative decoding or streaming, traditional generation waits for the full output before returning anything to the client. If an analyst asks the AI to summarize a lengthy incident, they might stare at a blank screen for a long time. By contrast, Mini-SGLang streams results and could use a speculative draft to cut that wait dramatically. A conventional pipeline also computes token-by-token with the full model, whereas Mini-SGLang can offload some work to a smaller model (reducing latency).

Lower Throughput under Load: Traditional pipelines often let the GPU idle during CPU preprocessing or between requests. They also may not dynamically batch requests, resulting in poor throughput if many small queries come in. Mini-SGLang’s overlap scheduling and continuous batching address this – as a result, it achieves higher token/sec and can handle more concurrent users without lag. For example, benchmarks show it outperforms a standard vLLM baseline in throughput due to these optimizations. Essentially, Mini-SGLang turns inference into a pipeline with minimal bubbles, whereas a naive approach might treat it as a sequential function call per query.

Inefficient Memory Use: Without a system like Radix cache or paged attention, a traditional pipeline will allocate a separate KV cache for each request and duplicate memory for identical prefixes. vLLM introduced a solution for single-node prefix sharing (PagedAttention), and SGLang extends this with Radix caching and hierarchical coordination. Traditional transformer servers (like straightforward HF Transformers or early generation frameworks) would miss out on these savings, leading to higher GPU memory usage and potential OOM issues when many long conversations are active. In addition, an out-of-the-box pipeline typically has no notion of cross-request caching, making repetitive prompts expensive. Mini-SGLang’s approach can be seen as merging the best of academic solutions (like vLLM’s block-level KV reuse) with additional scheduling smarts to ensure those benefits hold at scale.

Lack of Concurrency and Flexibility: Typical inference scripts block on one request until completion; handling multiple agents would require manual threading or async code, and ensuring fairness or priority is complex. Mini-SGLang handles concurrency internally – its scheduler can interleave tokens from different requests (especially if one request is waiting on I/O or drafting, another can use the GPU). It also provides compatibility layers (OpenAI-style API) so that integrating it into an SOC platform is easier. In short, traditional pipelines treat the model as a black-box function, while Mini-SGLang treats it as a service – optimizing at the system level (temporal scheduling, memory management, multi-request handling). The convergence of vLLM and SGLang techniques represents a new state-of-the-art: vLLM tackled spatial optimization (memory and parallel distribution), and SGLang focuses on temporal optimization (efficient token scheduling). Mini-SGLang combines elements of both, which is why it achieves better performance in real-world workloads than naive transformer use.


Deployment Considerations (CPU vs GPU): Deploying Mini-SGLang in a development vs production environment requires different tuning. For a CPU-based development environment such as an AWS m4 instance (which provides only CPU cores and no CUDA acceleration), one cannot expect real-time performance with large models – however, Mini-SGLang does support running on CPUs (it’s compatible with Intel Xeon architectures and even supports CPU attention kernels). In practice, for CPU-bound deployments the strategy is to use smaller model sizes and quantization to fit within limited memory and compute. For example, a developer might run a 7B parameter model quantized to 4-bit on an m4.xlarge for testing the agent logic. Mini-SGLang can leverage multiple CPU threads to parallelize the work, but features like FlashAttention or FlashInfer (optimized GPU kernels) won’t apply on CPU. Overlap scheduling still provides some benefit on CPU (overlapping tokenization and I/O with computation), but the main bottleneck will be raw compute speed. Therefore, for dev/test, one should aim for fast iteration with small models and maybe shorter context lengths. The framework’s OpenAI-compatible API makes it easy to swap in a mock smaller model locally and then switch to a bigger model on GPU in production. Logging and debugging are also easier on CPU, so using Mini-SGLang on an accessible CPU instance can be great for stepping through agent interactions, albeit at slower speed.

For production-grade deployments on GPU (e.g. using powerful NVIDIA H100 GPUs as noted), Mini-SGLang can unleash its full optimization arsenal. On an H100, one should enable the specialized kernels – Mini-SGLang integrates FlashAttention-3 for extremely fast attention computation during the prompt (prefill) phase and FlashInfer for optimized decode kernels on Hopper GPUs. These take advantage of H100 TensorCore and large shared memory capabilities to accelerate inference beyond what standard PyTorch kernels achieve. Additionally, production deployments often use tensor parallelism: for a model too large for one H100 (which has 80GB memory in the SXM form factor), Mini-SGLang can split the model across say 4×H100 (each hosting a slice of the network). The built-in support for tensor parallel and pipeline parallel means an organization can host a 70B+ model on multiple GPUs to serve more complex agent reasoning tasks. Another consideration is multi-instance vs multi-tenancy: one could run one Mini-SGLang server per GPU or a distributed mode. The choice depends on workload isolation needs. SGLang’s documentation describes a model gateway/router that can dispatch requests to different model instances or shards intelligently – this is useful if the SOC uses different models for different agents (e.g. a smaller model for triage, larger for deep analysis). On GPU servers, it’s also important to tune environment variables and settings: e.g. enabling pinned memory, ensuring --max-batch-size is set appropriately for expected concurrent load, and possibly using paged attention if many long contexts are expected (paged attention, from vLLM, prevents fragmentation by paging the KV cache to GPU memory as needed). In production, an H100-backed Mini-SGLang server should easily handle streaming outputs for dozens of concurrent sessions, but careful monitoring of memory and latency is needed. The engine exposes metrics (e.g. token latency, cache hit rate) which should be tracked to ensure the system meets SOC performance requirements. In summary, use the CPU deployment for functional testing and low-throughput scenarios, but leverage GPUs for the real workload. Modern GPUs like the H100 not only speed up inference by orders of magnitude, they also unlock features (FlashInfer, large batch sizes, quantization with INT8 support on TensorCores, etc.) that Mini-SGLang is optimized for. A possible deployment architecture is to have an API layer (which could itself run on CPU or lightweight instance) forwarding requests to one or more Mini-SGLang GPU workers – this decouples client handling from inference proper. Mini-SGLang’s design (with a frontend server and backend scheduler threads) inherently supports such separation.

Integrating Memory-Augmented Workflows with Mini-SGLang

The final piece is putting it all together: architecting the SOC workflows so that the memory systems of the agents are used effectively, and serving those workflows efficiently via Mini-SGLang. In a memory-augmented agent, typically a retrieval-augmented generation (RAG) pattern is used: before calling the LLM, the agent will retrieve relevant context from its knowledge stores (semantic or episodic memory) and include that in the prompt. The LLM then produces an output conditioned on both the prompt and the retrieved data. Mini-SGLang can significantly streamline RAG-based agents – it can manage the back-and-forth calls and data assembly without introducing too much latency. For instance, an agent might first query a vector database for “Windows server malware WXYZ” and get back a description of that malware (semantic memory), then call the LLM to analyze an alert using that information. Because Mini-SGLang is optimized for fast token output and can handle short queries very quickly, the overhead of doing an extra retrieval step followed by an LLM call is minimized. Moreover, if the same piece of knowledge (e.g. the malware description) is used multiple times, Radix Cache will ensure the LLM doesn’t repeatedly re-process it on each call. The synergy between memory and inference engine also appears in how agents chain reasoning: multi-step agent reasoning (Plan→Act→Observe loop) can involve many LLM invocations. Mini-SGLang’s fast scheduling allows these iterative calls to happen in near real-time, so an agent can reflect and revise plans without long delays. This is crucial for complex incident response scenarios where the agent might ask itself multiple sub-questions (each an LLM query) before finalizing an answer.

In this pipeline, specialized agents collaborate in seconds, passing context and results along: a Threat Intelligence agent gathers new IOCs, an Enrichment agent adds context (historical campaigns, geopolitical situation), a Correlation agent checks internal logs for related events, a Risk Assessment agent evaluates impacted assets and vulnerabilities, and a Remediation Planning agent formulates response actions. Each agent’s actions are informed by different memory types – e.g. the TI agent uses a knowledge base of threat feeds, the correlation agent queries past incidents (episodic memory), and the risk agent references an asset & vulnerability database (semantic memory). Combining these diverse data sources requires a unified memory architecture and results in rich, context-informed inputs for the LLMs. The fast coordination (all happening virtually instantly) is enabled by an orchestrator and an efficient inference engine that can handle the agents’ reasoning steps in parallel.

Consider an example retrieval-augmented investigation workflow for an incident response agent using Mini-SGLang:

1. Gather Context: The agent first retrieves relevant data for the incident at hand. For instance, it might query an internal knowledge base for the hostname or IP involved to get asset details and known vulnerabilities (semantic memory), and pull up past incident reports or alerts involving this entity (episodic memory). It may also fetch external threat intel if a specific malware or threat group is identified. These retrievals happen via vector similarity search or database lookup and are done before invoking the LLM. By grounding the next steps in authoritative data, the agent reduces mistakes and tailors its analysis to the organization’s environment.


2. Compose LLM Prompt: The agent composes a prompt for the LLM that includes: (a) a description of the current situation (e.g. “Multiple failed logins detected on server X followed by a suspicious process execution…”), (b) the retrieved contextual information (asset details, past incident notes, threat intel on the detected malware, etc.), and (c) instructions from procedural memory (e.g. “You are a security co-pilot. Analyze the incident and recommend containment steps following NIST guidelines.”). This prompt may be on the order of a few thousand tokens after inserting the knowledge – something Mini-SGLang can handle efficiently with its optimized context handling (using chunked prefill to avoid memory spikes for long prompts). The short-term memory from step 1 (recent relevant info) is now embedded in the LLM’s input.


3. LLM Inference via Mini-SGLang: The compiled prompt is sent to the Mini-SGLang server, which may load a large incident-response-focused LLM (for example, a 30B-70B parameter model fine-tuned for cybersecurity tasks). Thanks to streaming output, the agent begins receiving the model’s analysis within a couple of seconds, token by token. The overlap scheduler ensures that if multiple incidents are being analyzed concurrently by different agents, the GPU cycles are well-utilized and none of the analyses starve the others. As the model generates the response, it might produce a step-by-step reasoning or a recommended list of actions. If the output is lengthy (say a full incident report), speculative decoding could be employed to speed it up by having a smaller draft model hypothesize sections of the report in parallel. Throughout this, Radix caching is leveraged: if the agent iteratively calls the LLM (for example, after getting an initial summary, it might ask a follow-up question like “List specific hosts that were affected.”), the second call reuses the context from the first call that is unchanged (no need to recompute the analysis of the original logs). In a multi-agent setting, if another agent has a similar prompt prefix (e.g. the same corporate policy or a shared description of the environment), those requests also benefit from cache hits. Mini-SGLang effectively serves as the “brain” for all these agent queries, routing and executing them optimally.


4. Agent Acts on Output: Once the LLM’s output is complete (or even while it’s streaming), the incident response agent updates its procedural plan. For example, if the model recommended isolating a host and resetting credentials, the agent (or a connected orchestration system) now executes those actions via available tools (firewall API, Active Directory, etc.). These actions and the LLM’s findings are fed back into the agent’s episodic memory store – logging that “Host X isolated at 10:32, user accounts reset” along with the rationale from the LLM. This ensures the new knowledge becomes part of the record for future episodic recall. The agent might then prompt the LLM again for a remediation verification step (e.g. “Given we did X and Y, do we need to take any further action?”), continuing the loop until closure.



Throughout such workflows, Mini-SGLang provides the performance backbone so that each retrieval + generation cycle is as fast as possible. In an orchestration where multiple agents or agent steps run, Mini-SGLang’s ability to handle asynchronous, streaming, and batched requests ensures the whole pipeline doesn’t bottleneck on inference. For example, one agent can be generating a report while another quickly classifies an alert – the engine will intermix these jobs efficiently. This is important when designing an agentic SOC where you might have a Supervisory Agent coordinating sub-tasks among specialized agents. In the Trellix architecture, they indeed orchestrated different LLM calls for initial alert review vs deep investigation. With Mini-SGLang, one could deploy a similar multi-model strategy: have a small, fast model serve simple queries and a large, powerful model handle complex analyses, all through a unified serving layer.

Assigning Models, Memories, and Strategies per Agent: It is advisable to customize the model size and inference strategy for each agent role, balancing speed and capability. Here are some recommendations:

Alert Triage Agent: Use a smaller, high-speed model (e.g. ~2B-7B parameters) for lowest latency. The focus is on quick classification or dismissal of alerts, which typically requires recognizing known patterns – something a smaller model can do when fine-tuned on alert data. This agent leans on short-term memory (the current alert and recent related alerts) and some semantic knowledge of the organization (e.g. asset importance or past false positives). Inference strategy: run on CPU or a single modest GPU, enable streaming output to immediately flag if an alert looks malicious, and use batching to process multiple alerts in parallel during bursty periods. Since outputs are brief (e.g. “likely false positive” vs “possible credential theft”), speculative decoding is less useful here (the output isn’t long), but caching can help if many alerts share a common prefix structure (e.g. the same alert template). An example from industry is Amazon’s Nova model used for initial alert triage – chosen for its cost-effectiveness (100× cheaper than a large model) and fast responses. The small model filters and handles the bulk of routine decisions, passing only tricky cases forward.

Threat Intelligence Agent: This agent may need a somewhat larger model (e.g. 13B-30B) to synthesize information from threat reports, especially if generating advisories or performing causal analysis. It heavily uses semantic memory: a vast store of threat intel (indicators, TTPs, etc.) that it will retrieve and supply to the model. Because threat reports or intelligence briefs can be lengthy, using speculative decoding is beneficial to speed up generation of multi-paragraph outputs. Streaming is useful if an analyst is waiting for results of an intel query – partial info on emerging threats can be shown as it’s written. The agent’s episodic memory (past notable intel events) can also be retrieved to compare with new data (for instance, “this IOC appeared in a campaign we saw last year”). In deployment, a GPU-backed instance is recommended to handle the heavy text generation. The Radix cache can shine here: if multiple IOCs are related or an intel report is generated for several similar threats, shared context like the background on a threat actor can be cached and reused across those requests. For model assignment, one could deploy an open-source 13B model fine-tuned on threat intel reports. If the intel agent runs periodically (say generates a daily threat briefing), latency is less critical, but throughput and ability to ingest a lot of data (long context) is important – hence a model with long context window (8K+ tokens) served by Mini-SGLang’s chunked prefill is ideal.

Vulnerability Management Agent: This agent’s tasks (e.g. summarizing scan results, prioritizing vulnerabilities) can often be accomplished with a mid-sized model (~7B-13B) that has been infused with vulnerability domain knowledge (CVEs, CVSS scoring rubrics, etc.). Semantic memory integration is key: the agent should retrieve details on each vulnerability (from an internal CVE database or NVD feed) rather than relying on the model’s parametric knowledge. Procedural memory might be encoded as rules for prioritization (e.g. “if CVSS > 9 and asset is critical, flag immediately”). Many queries will be structured (e.g. “List the top 5 vulnerabilities to fix on Server Y”), which the model can answer concisely. As such, streaming is perhaps less crucial (the answers are short lists), but batch processing and caching are valuable because the agent might handle hundreds of assets in one go. Mini-SGLang can batch the analysis of vulnerabilities across assets, and reuse the prompt prefix that contains company policy on risk or the generic text of “Prioritize the following vulnerabilities…”. A concrete strategy could be to run this agent on a moderate GPU (or even CPU if performance allows) with the model quantized to reduce cost. If GPU, one could enable overlap scheduling to overlap data fetching from the vuln database (CPU-bound) with the model’s computations. Also, distributed scheduling isn’t typically needed unless scanning at massive scale, but if multiple machine nodes are used, ensuring the same asset’s vulnerabilities go to the same node might improve cache locality (as the asset context can be reused within that node’s KV cache).

Incident Response Agent: This is the most demanding agent – it must comprehend a large volume of data (logs, alerts, forensic data) and make complex decisions. A larger model (30B, 70B, or even ensemble approaches) is appropriate to capture the reasoning ability needed. This agent will use episodic memory extensively: the entire incident’s events are essentially the running context for the agent. Tools like Mini-SGLang allow very long prompts to be handled efficiently, but if an incident’s data exceeds the model context (say thousands of log lines), the agent may need to summarize or chunk the data and iteratively query the model (hierarchical RAG). Semantic memory is also used – e.g. knowledge of malware or attack techniques involved, drawn from threat intel databases. Procedural memory is critical in guiding the agent’s actions (often represented as a sequence of tasks or a decision tree the agent follows when new evidence comes in). From an inference standpoint, multi-GPU serving is often justified here: one might host a 70B parameter model across 4 GPUs to give the agent state-of-the-art reasoning quality. With Mini-SGLang on an H100 cluster, this model can still respond in reasonable time thanks to optimizations like FlashInfer and tensor parallelism. Streaming is very useful: as the incident agent writes its analysis or status report, the security team can see it in real time. Speculative decoding can cut down the turnaround time for long reports or post-incident summaries. Overlap scheduling helps if the agent is performing multiple subtasks (like summarizing different log sources concurrently – the CPU can prepare the next source’s prompt while GPU analyzes the current one). In addition, since incidents might unfold over hours with many iterative LLM calls, cache reuse is significant: the agent should keep static incident context (like the initial incident description) in the prompt for each call, which Mini-SGLang will cache so that repeated inclusion doesn’t incur extra cost. The difference between a traditional pipeline and Mini-SGLang becomes stark in this scenario – an investigation report that might take 60 seconds to generate with naive sequential decoding could potentially be done in a fraction of that time using streaming + speculative execution on a well-provisioned Mini-SGLang deployment. The net effect is that the incident response agent can iterate rapidly, approaching the problem like a human expert who is writing notes and conclusions continuously as new data comes in.


Finally, it’s worth noting the importance of orchestration and cost management when integrating these components. The SOC may not need a giant model for every single task – using the right tool for each job keeps the system efficient. The Trellix case study demonstrated this with a tiered model approach (small model for initial triage, large model for deep dive). Mini-SGLang can host multiple models concurrently or be deployed in multiple instances to facilitate such a strategy. Caching strategies (like Radix cache) further reduce duplicate work, effectively amortizing the cost of intelligence across many queries. As agents run 24/7, these optimizations translate directly to real-dollar savings and faster mean-time-to-detect/respond. By combining a robust memory architecture (ensuring agents always have the right context at hand) with an optimized serving framework (ensuring the AI reasoning is delivered quickly and efficiently), an agentic SOC can achieve a level of responsiveness and intelligence far beyond what naive implementations or human-only teams could. The architecture we’ve outlined provides a blueprint for building such a system with current technology, with each component – memory, models, and inference engine – playing a critical role in the overall performance and efficacy of autonomous SOC analysts.
